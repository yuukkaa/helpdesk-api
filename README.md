# Веб-сервис технической поддержки (Help Desk) — REST API + React Client

Полнофункциональный веб-сервис технической поддержки (Help Desk), состоящий из серверной части на **Laravel 13 (REST API + Sanctum)** и клиентского SPA-приложения на **React + TypeScript + Vite**.

---

## 1. Описание проекта и сущностей API

Сервис автоматизирует приём, классификацию, распределение и обработку обращений пользователей в службу технической поддержки.

### Основные сущности:
1. **Пользователи (`User`)** — учётные записи с ролевой моделью доступа:
   - `client` — создание обращений, просмотр своих заявок, переписка со специалистами, чтение опубликованных статей базы знаний;
   - `support` — просмотр всех заявок, взятие обращений в работу, смена статусов, ведение внутренних служебных заметок (`is_internal`), управление тегами и базой знаний, просмотр статистики и выгрузка отчётов в CSV;
   - `admin` — полный доступ, включая управление справочником категорий, учётными записями пользователей, принудительное назначение исполнителей и удаление заявок.
2. **Заявки (`Ticket`)** — основная сущность системы. Содержит тему (`subject`), описание (`description`), категорию, автора, ответственного специалиста (`assignee`), приоритет (`low`, `medium`, `high`, `urgent`) и статус жизненного цикла (`new` → `in_progress` ↔ `waiting_for_client` → `resolved` → `closed`).
3. **Категории (`Category`)** — тематический классификатор обращений (например, «Доступ и пароли», «Оплата и счета», «Технические ошибки»).
4. **Сообщения (`Message`) и Вложения (`Attachment`)** — переписка внутри заявки с поддержкой внутренних служебных заметок для сотрудников и прикрепления файлов через `Storage`.
5. **Метки (`Tag`)** — связь «многие-ко-многим» (`tag_ticket`) для гибкой маркировки заявок (`срочно`, `баг`, `аккаунт`, `бухгалтерия`).
6. **База знаний (`KnowledgeBaseArticle`)** — справочные статьи и инструкции для самообслуживания клиентов и формирования ответов специалистами (включая RAG-черновики через ИИ Gemini).

## 3. Установка и запуск проекта

### 3.1. Серверная часть (Laravel API)
```bash
# 1. Установка зависимостей PHP
composer install

# 2. Копирование конфигурации окружения и генерация ключа
cp .env.example .env
php artisan key:generate

# 3. Выполнение миграций и наполнение тестовыми данными
php artisan migrate --seed

# 4. Создание символической ссылки для публичного хранилища файлов
php artisan storage:link

# 5. Запуск локального сервера API (http://localhost:8000)
php artisan serve
```

### 3.2. Клиентское приложение (React + Vite)
Клиентское приложение расположено в каталоге `frontend/` и работает на отдельном порту (`http://localhost:5173`). Базовый адрес API задаётся в `frontend/.env` (`VITE_API_BASE_URL=http://localhost:8000/api`).

```bash
cd frontend
npm install
npm run dev
```

Настройки CORS на сервере находятся в файле `config/cors.php` и используют переменную окружения `CORS_ALLOWED_ORIGINS=http://localhost:5173,http://127.0.0.1:5173` (режим Bearer-токена, `supports_credentials = false`).

## 4. Запуск автотестов

Функциональные (Feature) тесты расположены в каталоге `tests/Feature/`:
- `tests/Feature/TicketApiTest.php` — тестирование жизненного цикла заявок, прав доступа, фильтрации, пагинации, загрузки файлов и бизнес-правил;
- `tests/Feature/HelpDeskEntitiesApiTest.php` — тестирование аутентификации Sanctum (`/api/register`, `/api/login`, `/api/user`, `/api/logout`), сообщений, категорий, меток, базы знаний, пользователей, статистики, экспорта CSV и заголовков CORS.

Тесты автоматически используют изолированную базу данных SQLite в памяти (`:memory:`, настроенную в `phpunit.xml`) и трейт `RefreshDatabase`.

Запуск всех тестов:
```bash
php artisan test
# или подробно с описанием сценариев:
php vendor/bin/phpunit --testdox
```

## 5. Логирование

- Каждый HTTP-запрос к API автоматически записывается middleware `App\Http\Middleware\LogApiRequests` в файл `storage/logs/laravel.log` (метод, URL, `user_id`, HTTP-статус ответа, время выполнения `duration_ms` в мс).
- Чувствительные поля (`password`, `password_confirmation`, `token`) и заголовки авторизации исключены из логирования.
- Ключевые события бизнес-логики записываются через фасад `Log`:
  - `Log::info` — регистрация, вход и выход пользователя, создание/обновление/удаление заявок, назначение специалиста, смена статуса, экспорт в CSV;
  - `Log::warning` — неудачные попытки входа, попытки доступа без прав (`403`), нарушения бизнес-правил (`409`);
  - `Log::error` — внутренние сбои сервера (`500`) и ошибки внешних сервисов.
